# OFC Poker Implementation Prompt Outline

This document is the ordered implementation plan for building OFC Poker with a coding agent. Each numbered section is intended to be issued as a separate prompt. The sequence favors small, reviewable increments, establishes deterministic game behavior before UI or networking, and includes dedicated quality passes rather than treating tests and design as cleanup work.

## Project-wide instructions for every prompt

Include these instructions, or their equivalent, whenever a prompt is given to the coding agent:

- Read `README.md` and the relevant files under `docs/` before changing code. Treat `docs/requirements.md` and `docs/reference/open-face-chinese-poker-rules-engine-spec.md` as the product and rules sources of truth.
- Use TypeScript in strict mode. Prefer explicit domain types and dependency injection over hidden global state.
- Keep the game engine, AI, and data-provider independent of React, browser APIs, Three.js, and each other except through documented interfaces.
- Make the smallest coherent change for the prompt. Do not implement later prompts early unless a small prerequisite is necessary.
- Preserve existing working behavior and user changes. Avoid committing secrets, Playroom credentials, generated build output, or machine-specific files.
- Add or update tests with every behavior change. Use deterministic clocks, random-number generators, deck order, and player IDs in tests.
- Run the relevant format, lint, type-check, unit, integration, build, and end-to-end commands. Report commands and results, including anything that could not be run.
- Update `docs/tasks.md` with completed work and requirement references. Update `docs/workflows.md` when commands or developer workflows change. Mark an item in `docs/requirements.md` complete only after its acceptance criteria are demonstrably satisfied.
- End each prompt with a concise summary of files changed, decisions made, tests run, and remaining risks or follow-up work.

## Definition of done

The project is complete only when all requirements are checked, all automated quality gates pass from a clean install, a production build works at the configured GitHub Pages repository path, local AI play makes no multiplayer-service requests, and the documented multiplayer flow works for two through four browser clients.

## Prompt 1 — Resolve architecture decisions and define contracts

### Goal

Turn the current documentation into a consistent implementation blueprint before scaffolding. Resolve the conflict between `docs/architecture/system.md` (Next.js) and the Vite/React decisions elsewhere. Default to React + Vite because the dependency and code architecture documents explicitly select it and the application is a static GitHub Pages deployment. Resolve the workspace-list discrepancy by including the separately designed AI package. Define package boundaries, dependency direction, runtime ownership, state authority, and browser URL behavior.

Create lightweight architecture decision records or update the architecture docs to describe:

- npm workspaces: `client`, `game-engine`, `ai-player`, and `data-provider`;
- pure, deterministic game-engine events and state transitions;
- a provider interface with local and Playroom implementations;
- a configurable AI interface that depends only on public engine state/actions;
- a client-owned game runner that coordinates engine, provider, AI, and view ports;
- a replaceable game-view interface with a React Three Fiber implementation;
- host-authoritative multiplayer, action validation, event IDs, and reconnect/snapshot behavior;
- lobby creation/join URLs that work with static GitHub Pages hosting; and
- fixed lobby settings copied into immutable game configuration at lobby creation.

### Acceptance criteria

- The docs name one frontend framework/build tool consistently: React + Vite, with the stale Next.js statement removed or explicitly superseded.
- A package dependency diagram or written dependency rules prevent cyclic dependencies and prevent domain packages from importing client/UI code.
- Public interfaces and ownership are described for game events, snapshots, providers, AI decisions, runner, and view.
- Multiplayer authority, disconnect/reconnect, invalid action, duplicate event, capacity, and late-join behavior are specified.
- GitHub Pages base-path and lobby-link routing constraints are addressed without requiring a server rewrite rule.
- Every requirement in `docs/requirements.md` maps to at least one planned prompt.
- No production code is added in this prompt.

## Prompt 2 — Scaffold the npm workspace and quality gates

### Goal

Create the monorepo foundation and a minimal runnable React/Vite client. Configure npm workspaces, shared TypeScript settings, formatting, linting, unit-test tooling, and root scripts. Keep package exports and scripts consistent so each package can be built and tested independently and from the root.

### Acceptance criteria

- `npm install` from the repository root produces one lockfile and recognizes all four workspaces.
- Root scripts cover at least `dev`, `build`, `typecheck`, `lint`, `test`, and `test:e2e`; aggregate scripts fail if a workspace fails.
- All packages use strict TypeScript and expose intentional entry points rather than source-path imports.
- The client renders a basic accessible application shell through Vite and builds as a static application.
- Unit-test configuration supports DOM tests in the client and fast non-DOM tests in domain packages.
- Formatting, linting, type-checking, unit tests, and production build pass.
- `docs/workflows.md` contains clean-install, development, test, and build commands.

## Prompt 3 — Build cards, deck, and poker-hand evaluation

### Goal

Implement the pure card primitives and conventional poker evaluator inside `game-engine`. Establish canonical card identity, parsing/serialization, deterministic deck creation/shuffling, three-card front-row evaluation, five-card evaluation, comparison keys, and tie behavior. This evaluator is foundational and must be independently trustworthy before OFC rules are layered on it.

### Acceptance criteria

- A standard deck contains exactly 52 unique cards with no jokers.
- Shuffling accepts an injected random source or deterministic deck order for repeatable tests.
- Five-card evaluation handles high card through royal flush, including ace-low straights, kickers, and exact ties.
- Three-card evaluation recognizes only high card, pair, and three of a kind; straights and flushes have no special front-row rank.
- Suits never break ties.
- Evaluation results are immutable, serializable, and suitable for row legality comparison.
- Table-driven tests cover every hand class, important kicker cases, wheel straights, royal-flush identification, and equal hands.
- Package lint, type-check, tests, and build pass.

## Prompt 4 — Implement the deterministic OFC placement engine

### Goal

Implement the event-driven standard OFC hand lifecycle: seats, dealer position, turn order, deck/deal state, initial five-card placement, eight single-card placements, row capacities, committed-card immutability, and hand completion. Model commands/events and errors explicitly so local, AI, and multiplayer callers all use the same validation path.

### Acceptance criteria

- A hand supports exactly two to four uniquely identified players and a 52-card deck.
- The first action is left of the dealer and action proceeds clockwise according to the documented timing policy.
- Each player places all five initial cards without exceeding row capacities, then places eight cards one at a time.
- A placement is allowed even if it may eventually foul; full-row placement, wrong-turn action, unknown/duplicate card, moving a committed card, and malformed events are rejected without mutating state.
- Completed boards contain exactly `3 / 5 / 5` cards and all dealt cards are accounted for exactly once.
- State transitions are pure and deterministic from the same initial state and ordered events.
- State and events are serializable and versioned for provider transport.
- Unit tests cover valid full-hand flows, every validation boundary, turn changes, and dealer rotation policy.

## Prompt 5 — Add legality, royalties, pairwise scoring, and Fantasyland

### Goal

Complete the rules engine according to the rules reference. Evaluate board legality, calculate all front/middle/back royalties, score every unordered player pair using standard 1–6 scoring, preserve zero-sum totals, and determine Fantasyland entry/re-entry and reveal state.

### Acceptance criteria

- Board legality is based on `back >= middle >= front`, with adjacent equality allowed.
- Fouled-versus-legal and fouled-versus-fouled scoring exactly matches the reference.
- Legal pair scoring includes row results, scoop bonus, and net royalties; tied rows score zero.
- All royalty tables and royal-flush distinctions match the reference.
- Two-, three-, and four-player totals are calculated pairwise and always sum to zero.
- Fantasyland qualification, simultaneous Fantasyland players, requalification, face-down state, and showdown reveal follow the documented policies.
- Round output includes per-row evaluations, foul status, royalties, pairwise breakdowns, total deltas, and next-hand Fantasyland status.
- Exhaustive table-driven examples cover royalty boundaries, fouls, ties, scoops, multi-player scoring, and Fantasyland conditions.

## Prompt 6 — Harden and document the game engine

### Goal

Perform a focused engine-quality pass before consumers are built. Add invariant/property-based testing where useful, public API documentation, snapshot migration/version handling, and multi-hand match state including cumulative score and dealer rotation. Keep policy choices explicit and configurable only where the rules reference identifies ambiguity.

### Acceptance criteria

- Tests generate or exercise many valid decks/placements and prove no duplicate cards, valid capacities, deterministic replay, and zero-sum scoring.
- Replaying the same event log yields the same state and resolution.
- Multi-hand matches preserve cumulative scores and correctly rotate the dealer and Fantasyland status.
- Unsupported snapshot/event versions fail with typed, actionable errors.
- Public engine APIs are documented with examples and do not expose mutable internal collections.
- Engine coverage is measured, meaningful uncovered branches are addressed, and no skipped/focused tests remain.
- The package passes lint, type-check, tests, and build independently.

## Prompt 7 — Define the data-provider contract and local provider

### Goal

Implement a transport-neutral data-provider package and a complete in-memory/local provider for development, testing, and AI-only play. The provider must communicate lobby metadata, immutable settings, player presence, validated action requests, authoritative snapshots/events, and lifecycle changes without knowing OFC rules.

### Acceptance criteria

- The contract covers create, join, leave/disconnect, subscribe, submit action, publish authoritative state, and dispose/cleanup behavior.
- Lobby settings and capacity are fixed after creation and exposed read-only to joiners.
- The local provider supports two to four simulated clients in one process/test environment, with deterministic IDs and optional injected latency/error hooks.
- Duplicate actions/events are idempotent and subscriptions can be safely removed.
- Capacity, missing lobby, invalid lifecycle, host departure, reconnect, and late-join snapshot behavior match the architecture decision.
- Contract tests are reusable against any provider implementation.
- Local-provider tests use no network and no Playroom dependency or service credentials.
- Package lint, type-check, tests, and build pass.

## Prompt 8 — Implement and contract-test the Playroom provider

### Goal

Integrate Playroom Kit behind the provider contract. Verify the current installed SDK API while implementing rather than leaking SDK concepts into the rest of the application. Use host-authoritative action validation and state publication, safe lifecycle cleanup, and shareable lobby identifiers/links.

### Acceptance criteria

- Playroom imports exist only inside the Playroom adapter (and its tests/configuration).
- Creating and joining a room requires no application account and supports a display name.
- Only the authoritative host advances engine state; peers submit action requests and receive authoritative updates.
- Sender/seat identity is derived from trusted provider identity rather than arbitrary action payload fields.
- Duplicate, stale, malformed, unauthorized, and out-of-turn actions cannot alter authoritative state.
- Reconnect and late join restore the latest authoritative snapshot; host change follows the documented policy.
- Adapter cleanup removes listeners and avoids repeated initialization during client rerenders.
- Reusable provider contract tests pass with a mocked/fake Playroom boundary, and any manual sandbox test steps are documented.
- No secret is embedded in client code or committed files.

## Prompt 9 — Build configurable AI players

### Goal

Create the independent `ai-player` package with a stable decision interface and internally configurable strategy. Provide at least a legal baseline bot and a stronger heuristic bot whose style and strength can be tuned without modifying the game engine. Make all decisions deterministic when seeded.

### Acceptance criteria

- AI consumes only public player-visible state and returns ordinary engine actions.
- Every AI action passes the same engine validation as a human action and always selects an available row.
- Configuration supports named difficulty/strategy and documented parameters such as risk tolerance, royalty preference, foul avoidance, and optional think delay.
- A seeded random source makes decisions and tests repeatable.
- The baseline strategy can complete arbitrary valid hands; the heuristic strategy evaluates future legality and scoring opportunity rather than choosing rows uniformly.
- Tests cover row-capacity pressure, initial-five placement, single-card turns, near-foul decisions, Fantasyland placement, and deterministic behavior.
- A simulation test completes many games with two to four mixed AI players without hangs or invalid actions and reports basic foul-rate diagnostics without flaky assertions.

## Prompt 10 — Implement the app shell, settings form, and static routing

### Goal

Build the polished pre-game client experience: home screen, human display name, mode choice (multiplayer or AI lobby), player count, supported game settings, validation, lobby creation, and join-link handling. Use semantic HTML and ensure static GitHub Pages URLs survive refresh/navigation constraints.

### Acceptance criteria

- A user can choose multiplayer or local AI, configure valid defaults, and create a lobby from an accessible form.
- Settings have typed defaults, inline validation, helpful errors, keyboard support, labels, focus handling, and sensible narrow/wide layouts.
- The form prevents unsupported player counts and makes clear that settings cannot change after lobby creation.
- Join URLs preserve the lobby identifier using the routing approach selected in Prompt 1 and work beneath a repository base path.
- Joining displays immutable lobby settings and does not offer controls that imply they can be changed.
- Provider choice is explicit dependency wiring, not conditional logic spread through UI components.
- Component/unit tests cover validation, create flow, join parsing, invalid links, and immutable settings display.
- No multiplayer SDK initializes merely by loading the home page or selecting AI mode.

## Prompt 11 — Implement the game runner and lobby lifecycle

### Goal

Build the client-side game runner that coordinates a game engine, provider, optional AI players, and view adapter. Implement lobby waiting, seat assignment, ready/start rules, authoritative state updates, action submission, reconnect status, hand transitions, and match restart/new-lobby behavior without coupling React components to transport internals.

### Acceptance criteria

- The runner is instantiated once per active lobby and reliably disposed when leaving or switching lobbies.
- A lobby starts only with its configured two-to-four seats occupied by humans and/or configured AI players.
- All human and AI actions pass through the same engine command path.
- Non-host clients never deal cards or calculate an independent authoritative state.
- Duplicate delivery, delayed delivery, reconnect, and unmount/remount do not double-apply actions.
- The runner exposes a typed, read-only view model including whose turn it is, connection state, legal action availability, scores, and errors.
- Starting another hand preserves match totals, rotates the dealer, and applies Fantasyland status.
- Unit/integration tests use the local provider and fake view to cover complete lifecycle and cleanup.

## Prompt 12 — Establish the minimal 3D game-view design system

### Goal

Create a minimal, readable tabletop presentation using React Three Fiber. Define camera, lighting, card geometry/materials, board layout for two through four seats, animation principles, color/typography tokens, responsive behavior, and a DOM overlay for controls and text that should remain accessible. Keep rendering behind the game-view boundary.

### Acceptance criteria

- The scene clearly distinguishes front, middle, and back rows and their `3 / 5 / 5` capacities for every seat count.
- Cards have legible rank/suit faces, consistent backs, visible selected/valid-target states, and stable orientation for the local player.
- Camera and layout remain usable at representative mobile and desktop viewport sizes without clipping essential controls.
- Motion is restrained, respects reduced-motion preferences, and does not block input correctness.
- Status, scores, buttons, error messages, and essential card information have an accessible DOM representation; gameplay does not depend on color alone.
- The WebGL canvas has a graceful unsupported/error fallback.
- View components consume typed view-model data and emit view actions; they do not import the engine reducer or provider SDK.
- Rendering/component tests cover seat layouts, row labels/capacities, accessibility semantics, and fallback behavior.

## Prompt 13 — Complete human card-placement and showdown UX

### Goal

Connect the game view to the runner and implement the full human interaction loop. Support initial-five arrangement, single-card placement, confirmation where appropriate, turn feedback, permanent committed placements, Fantasyland private arrangement, showdown reveal, score breakdown, and next-hand flow.

### Acceptance criteria

- A player can place the initial five cards into any non-overflowing rows and clearly distinguish staged from committed cards.
- Single-card turns expose only valid non-full row targets and commit exactly one placement.
- Committed cards cannot be dragged, clicked, or otherwise moved; rejected actions restore coherent UI and announce an error.
- Keyboard and pointer users can complete every placement action without relying solely on 3D hit targets.
- Opponents' face-up cards update from authoritative state; Fantasyland cards stay hidden until showdown.
- Turn, dealer, connection/reconnect, waiting, foul, royalty, scoop, and Fantasyland states are clearly communicated.
- Showdown includes a comprehensible pairwise and total score breakdown and an explicit next-hand action.
- Component/integration tests cover normal and Fantasyland hands, invalid attempts, full rows, disconnect feedback, and showdown.

## Prompt 14 — Deliver the complete offline AI-lobby mode

### Goal

Integrate local provider, runner, and AI strategies into a production-quality local-play mode. A human should be able to start immediately with one to three AI opponents, complete multiple hands, and tune internal bot profiles through a centralized configuration without contacting Playroom.

### Acceptance criteria

- AI mode supports a total of two, three, or four seats with exactly one local human and the remaining seats filled by AI.
- Creating and playing an AI lobby never initializes Playroom, opens a WebSocket, or sends a multiplayer-service request; an automated test asserts this boundary.
- AI turns progress without manual intervention, cannot act twice, and pause/stop cleanly when the runner is disposed.
- The UI communicates AI thinking without making automated tests depend on real time.
- Multiple hands preserve scores, dealer rotation, and Fantasyland.
- Strategy/difficulty is configured in one internal registry and can be changed without engine or view edits.
- An integration test plays a full human-plus-AI hand using deterministic cards and validates the resulting score screen.

## Prompt 15 — Deliver the complete multiplayer lobby flow

### Goal

Integrate the Playroom provider into the production client and complete the invite-by-link experience for two to four real browser clients. Add clear waiting-room, joining, full/missing lobby, disconnect, reconnect, and host lifecycle feedback while retaining host-authoritative validation.

### Acceptance criteria

- A player creates a multiplayer lobby and receives a copyable shareable URL and visible room code if supported.
- Two, three, and four clients can join without accounts, see consistent fixed settings/seats, and start at the configured capacity.
- Each client sees only its own actionable card while all public placements synchronize consistently.
- Invalid or malicious client payloads, duplicate actions, and stale actions do not mutate the game.
- Refresh/reconnect restores the current seat and state when supported by the documented provider policy, or displays a precise recovery path otherwise.
- Full, nonexistent, incompatible-version, initialization-failure, and disconnected states have user-facing recovery actions.
- Lobby/service resources and subscriptions are cleaned up when leaving.
- Integration tests exercise the adapter boundary; a documented manual smoke test covers real Playroom behavior and its free-tier constraints.

## Prompt 16 — Expand unit, integration, accessibility, and resilience coverage

### Goal

Audit every implemented feature against the requirements and fill quality gaps before browser end-to-end automation. Focus on failure paths, package boundaries, accessibility, deterministic behavior, resource cleanup, and regressions likely in multiplayer or 3D UI code.

### Acceptance criteria

- A test traceability table maps every requirement and important rule to one or more automated tests.
- Coverage includes all engine rules, AI action types, both provider modes, form/lobby flows, runner lifecycle, 3D/DOM view states, and errors.
- Automated accessibility checks run on home, waiting-room, active-game, and showdown states; critical violations are fixed.
- Tests cover slow/duplicate/out-of-order provider messages, reconnect, disposal, invalid snapshots, SDK failure, and WebGL fallback.
- Tests use deterministic fixtures and fake time where needed; no arbitrary sleeps or flaky random assertions remain.
- Coverage thresholds are justified by package, enforced in CI, and do not encourage low-value assertions.
- `npm test`, lint, type-check, and build pass from the root with no skipped/focused tests or unexplained warnings.

## Prompt 17 — Add Playwright end-to-end journeys

### Goal

Implement browser-level tests for the highest-value user journeys using the production build and local provider/emulated multiplayer transport so tests do not consume Playroom quota. Use multiple browser contexts for multiplayer behavior and deterministic test hooks that are excluded or safely disabled in normal production use.

### Acceptance criteria

- Playwright runs against a production-style static build at the repository base path.
- Tests cover settings validation, creating an AI lobby, completing a deterministic AI hand, score display, and starting the next hand.
- Multi-context tests cover creating a lobby, joining by copied link, fixed settings, synchronized placements, showdown, and two-to-four player capacity behavior without the real paid/quota service.
- Tests cover invalid lobby links, full lobby, refresh/reconnect policy, and a WebGL fallback or supported visual smoke path.
- Selectors prioritize roles, labels, and stable user-facing semantics over implementation-specific CSS.
- Screenshots/traces are retained on failure, but generated artifacts are gitignored.
- E2E tests do not depend on external service availability, real credentials, arbitrary long waits, or execution order.
- The root `test:e2e` workflow is documented and passes locally.

## Prompt 18 — Configure CI and GitHub Pages deployment

### Goal

Create secure GitHub Actions workflows that validate pull requests and deploy the static client as a GitHub repository page on pushes to `main`. Ensure Vite asset paths, routing, caching, permissions, and concurrency are correct for the repository-page URL.

### Acceptance criteria

- Pull requests run clean install, lint, type-check, unit/integration tests, production build, and the agreed E2E subset.
- Pushes to `main` deploy only after required validation succeeds.
- The deployment uses current GitHub Pages artifact/deploy actions, minimal permissions, pinned action versions, and deployment concurrency protection.
- The Vite base path is configurable for the repository name and generated asset URLs work under that path.
- Directly opening and refreshing supported home/join URLs works with the chosen static-routing strategy.
- CI and deployment do not require Playroom credentials and do not spend Playroom quota.
- `docs/workflows.md` documents repository settings, local reproduction, deployment URL, and troubleshooting.
- Workflow syntax and a local production build are validated.

## Prompt 19 — Final requirement audit and release-quality polish

### Goal

Perform a final evidence-based release review. Do not add speculative features. Verify each requirement, run the full clean-install pipeline, test representative mobile/desktop layouts, inspect bundle/runtime warnings, remove dead code and placeholders, and make the documentation sufficient for a new contributor and a player.

### Acceptance criteria

- All 13 requirements have explicit verification evidence and are checked only when satisfied.
- From a clean checkout, documented commands install, lint, type-check, test, build, and run E2E successfully.
- A two-, three-, and four-player game is verified through local automated coverage; a real-service multiplayer smoke test is documented with its date/result if credentials and quota are available.
- AI-only play is verified to make zero Playroom requests.
- Mobile and desktop home, lobby, placement, Fantasyland, and showdown views are reviewed for readability, overflow, keyboard access, reduced motion, and WebGL fallback.
- Production output contains no secrets, debug-only controls, source-path imports, TODO placeholders for required behavior, or unexplained console errors.
- README explains the game, prerequisites, development, testing, architecture, deployment, known Playroom free-tier limitations, and how to create/join both lobby modes.
- `docs/tasks.md`, `docs/workflows.md`, architecture docs, and requirement status reflect the delivered implementation.
- The final report lists commands run, results, deployment URL or exact remaining deployment step, known limitations, and no unsupported claims.
